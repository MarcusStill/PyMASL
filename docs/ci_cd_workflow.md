# GitHub Actions CI/CD Workflow

В этом репозитории настроен автоматический запуск тестов с помощью GitHub Actions.
Файл конфигурации находится по пути `.github/workflows/ci.yml`.

## Как это работает

*   **dev:** При отправке (push) любых изменений в ветку `dev` GitHub Actions автоматически запускает тесты (пайплайн CI).
*   **master:** При создании Pull Request (PR) из ветки `dev` в ветку `master` также автоматически запускаются тесты. Это позволяет убедиться, что сливаемый код работоспособен.

## Настройка Branch Protection Rules в GitHub

Чтобы запретить прямое слияние кода в `master` без успешного прохождения тестов, вам необходимо настроить правила защиты веток в настройках репозитория на GitHub:

1.  Откройте ваш репозиторий на GitHub.
2.  Перейдите в **Settings** (Настройки) -> **Branches** (Ветки).
3.  Нажмите кнопку **Add branch protection rule** (Добавить правило защиты ветки).
4.  В поле **Branch name pattern** введите `master`.
5.  Включите опцию **Require a pull request before merging** (Требовать Pull Request перед слиянием).
6.  Включите опцию **Require status checks to pass before merging** (Требовать успешного прохождения проверок статуса перед слиянием).
7.  В появившемся поле поиска найдите и выберите проверку с именем `test` (это имя задания в нашем `ci.yml`).
8.  (Опционально) Рекомендуется также включить **Require branches to be up to date before merging**, чтобы гарантировать тестирование актуального кода.
9.  Нажмите **Create** (или **Save changes**), чтобы сохранить правило.

## Правильный рабочий процесс (Workflow)

Ваш процесс работы с двумя ветками абсолютно корректен и является стандартной практикой:

1.  **Разработка:** Вы ведете разработку, создаете новые коммиты и отправляете их в ветку `dev`.
    ```bash
    git checkout dev
    # ... пишем код ...
    git add .
    git commit -m "Добавлена новая фича"
    git push origin dev
    ```
2.  **Проверка:** После отправки в `dev` на GitHub автоматически запускаются тесты. Вы можете посмотреть их результаты во вкладке **Actions**. Если тесты упали, вы исправляете ошибки в `dev` и снова отправляете изменения.
3.  **Создание Pull Request:** Когда разработка фичи завершена и тесты в `dev` зеленые, вы переходите на GitHub и создаете **Pull Request (PR)** из ветки `dev` в ветку `master`.
4.  **Слияние (Merge):** GitHub еще раз запустит тесты для PR. Если они успешны и вы настроили правила защиты ветки, кнопка `Merge pull request` станет зеленой. Вы нажимаете ее, и изменения сливаются в `master`.
5.  **Обновление локального master:** Не забудьте обновить вашу локальную ветку `master`:
    ```bash
    git checkout master
    git pull origin master
    git checkout dev
    ```

С такой настройкой ветка `master` всегда будет содержать стабильный, проверенный тестами код.
