# Инструкция по CI/CD и Git Workflow

## 1. Настройка CI/CD в GitHub Actions
Проект уже содержит конфигурацию GitHub Actions в файле `.github/workflows/ci.yml`.
Этот рабочий процесс автоматически запускается:
- При каждом `push` (отправке коммита) в ветку `dev`.
- При создании `pull_request` в ветку `master`.

В процессе выполнения:
1. Клонируется код из репозитория.
2. Устанавливается Python версии 3.12.
3. Устанавливаются системные зависимости (Xvfb для тестов с графическим интерфейсом).
4. Подготавливаются и устанавливаются зависимости из файла `requirements.txt`.
5. Запускаются тесты с помощью pytest.

Таким образом, базовая автоматизация уже настроена.

## 2. Настройка Branch Protection Rules в GitHub
Чтобы запретить слияние (merge) в ветку `master`, если тесты падают, нужно настроить правила защиты веток (Branch Protection Rules) в настройках репозитория на GitHub:

1. Откройте ваш репозиторий на GitHub.
2. Перейдите в **Settings** (Настройки).
3. В левом меню выберите **Branches** (Ветки).
4. В секции "Branch protection rules" нажмите **Add rule** (Добавить правило).
5. В поле **Branch name pattern** введите `master`.
6. Поставьте галочку **Require a pull request before merging** (Требовать pull request перед слиянием).
7. Поставьте галочку **Require status checks to pass before merging** (Требовать успешного прохождения проверок статуса перед слиянием).
   - В появившемся поле поиска введите имя вашего job-а из файла ci.yml (по умолчанию это `test`) и выберите его.
8. (Опционально) Поставьте галочку **Require approvals** (Требовать одобрения), если хотите, чтобы код смотрел еще один разработчик.
9. Нажмите **Create** (Создать).

## 3. Рекомендуемый Git Workflow
Если у вас две основные ветки (`dev` и `master`), правильный процесс работы выглядит так:

1. **Разработка в `dev`**:
   Все новые фичи, исправления багов и доработки делаются либо прямо в `dev`, либо в отдельных ветках (feature-branches), которые затем вливаются в `dev`.
   ```bash
   git checkout dev
   git pull origin dev
   # ... внесение изменений ...
   git add .
   git commit -m "Добавлена новая фича"
   git push origin dev
   ```
   *После push в `dev` автоматически запустятся тесты в GitHub Actions.*

2. **Проверка работоспособности**:
   Убедитесь, что CI/CD в ветке `dev` прошел успешно (зеленая галочка рядом с коммитом).

3. **Создание Pull Request**:
   Когда вы готовы перенести изменения в `master` (например, для релиза):
   - Перейдите в интерфейс GitHub.
   - Создайте **Pull Request** из ветки `dev` в ветку `master`.
   - CI/CD снова запустит тесты для этого Pull Request.

4. **Слияние (Merge) в `master`**:
   - Если тесты успешно пройдены и PR проверен (при необходимости), нажмите кнопку **Merge pull request**.
   - Теперь ваши проверенные изменения находятся в ветке `master`.

**Почему не стоит коммитить напрямую в `master`?**
Ветка `master` должна всегда содержать стабильный, проверенный и готовый к продакшену код. Работа через `dev` и Pull Request-ы гарантирует, что случайные ошибки или падающие тесты не попадут в стабильную версию продукта.
