# Настройка CI/CD и рабочий процесс Git

Этот документ описывает настроенный процесс CI/CD (Continuous Integration / Continuous Deployment) в данном проекте и правильный рабочий процесс (workflow) с использованием веток `dev` и `master`.

## Как устроен рабочий процесс (Workflow)

Ваш текущий подход к работе с двумя ветками абсолютно правильный и является стандартом индустрии (упрощенная версия GitFlow или GitHub Flow).

1. **Ветка `dev` (разработка):**
   * Все новые наработки, функции и исправления отправляются (push) в ветку `dev`.
   * При каждом пуше в ветку `dev` GitHub Actions автоматически запускает пайплайн (тесты, проверки).
   * Вы проверяете работоспособность изменений.

2. **Ветка `master` (стабильная версия):**
   * Это ветка, в которой всегда должна находиться стабильная, готовая к релизу версия проекта.
   * Прямые коммиты (push) в `master` **запрещены**.
   * Все изменения попадают в `master` исключительно через **Pull Request** из ветки `dev` (или других feature-веток).

## Пайплайн GitHub Actions

В проекте уже создан файл настроек GitHub Actions по пути `.github/workflows/ci.yml`.

Он настроен на запуск автоматических проверок в следующих случаях:
1. Выполнен `push` в ветку `dev`.
2. Открыт или обновлен `Pull Request` в ветку `master`.

Этот пайплайн (job `test`):
- Устанавливает Ubuntu и Python 3.12.
- Устанавливает нужные системные пакеты (xvfb) и зависимости Python.
- Запускает тесты `pytest` из каталога `tests/` с нужными переменными окружения базы данных.

Если тесты падают, пайплайн будет отмечен красным крестиком (fail), и вам нужно будет разобраться с ошибками, прежде чем изменения можно будет слить в `master`.

## Как настроить защиту ветки `master` (Branch Protection Rules)

Чтобы убедиться, что никто не сможет случайно сломать ветку `master` или влить в нее код с падающими тестами, вам необходимо настроить правила защиты веток в настройках репозитория на GitHub.

Выполните следующие шаги в веб-интерфейсе GitHub:

1. Перейдите на страницу вашего репозитория на GitHub.
2. Откройте вкладку **"Settings"** (Настройки).
3. В левом меню выберите **"Branches"** (Ветки).
4. Нажмите кнопку **"Add branch protection rule"** (Добавить правило защиты ветки).
5. В поле **"Branch name pattern"** введите `master`.
6. Отметьте следующие важные чекбоксы:
   * **Require a pull request before merging** (Требовать Pull Request перед слиянием).
     * Это отключит возможность делать прямой `git push` в ветку `master`. Слияние будет возможно только через PR из `dev`.
   * **Require status checks to pass before merging** (Требовать успешного прохождения проверок статуса перед слиянием).
     * Это ключевой пункт для работы CI/CD. В появившемся поле поиска ниже (Status checks that are required) найдите и добавьте задачу (job), которая запускает тесты (обычно она называется `test` — так же, как в `ci.yml`).
     * Теперь кнопку "Merge" в Pull Request невозможно будет нажать, если тесты завершились с ошибкой.
7. Прокрутите вниз и нажмите **"Create"** (или "Save changes").

## Итог ежедневной работы

1. Вы пишете код и делаете коммиты локально в ветку `dev`.
2. Делаете `git push origin dev`.
3. GitHub Actions запускает тесты.
4. Если тесты пройдены и функционал готов к релизу, вы заходите на GitHub, открываете Pull Request из `dev` в `master`.
5. GitHub Actions снова проверит этот PR (на всякий случай).
6. Если загорается зеленая галочка проверок — вы нажимаете "Merge pull request".
7. (Опционально) Переключаетесь локально на `master` (`git checkout master`), делаете `git pull`, и возвращаетесь в `dev`.
