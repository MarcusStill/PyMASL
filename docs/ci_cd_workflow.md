# Инструкция по настройке CI/CD рабочего процесса (GitHub Actions)

В данном проекте настроен процесс непрерывной интеграции (CI) с использованием GitHub Actions. Конфигурация находится в файле `.github/workflows/ci.yml`.

## Рабочий процесс (Workflow)

Проект использует стратегию с двумя основными ветками:
1. `master` — стабильная ветка. В ней находится проверенный, рабочий код, готовый к релизу (или уже в релизе).
2. `dev` — ветка разработки. Сюда отправляются (пушатся) все новые наработки и изменения.

### Как правильно работать:

1. Разработка ведется локально, коммиты делаются в ветку `dev`.
2. Вы отправляете изменения в GitHub (`git push origin dev`).
3. GitHub Actions автоматически запускает тесты для ветки `dev` (см. файл `ci.yml`, триггер `on: push: branches: [dev]`).
4. Если тесты проходят успешно, вы создаете **Pull Request (PR)** из ветки `dev` в ветку `master`.
5. При создании Pull Request снова запускаются тесты для проверки того, что слияние не сломает `master` (триггер `on: pull_request: branches: [master]`).
6. После успешного прохождения тестов и ревью кода, Pull Request можно вливать (merge) в `master`.

## Настройка Branch Protection Rules в GitHub

Чтобы гарантировать, что никто случайно не сломает ветку `master` напрямую и что все изменения обязательно проходят тесты перед слиянием, нужно настроить **Branch Protection Rules** в настройках репозитория на GitHub:

1. Откройте репозиторий на GitHub.
2. Перейдите на вкладку **Settings**.
3. В левом меню выберите **Branches**.
4. В разделе **Branch protection rules** нажмите кнопку **Add branch protection rule**.
5. В поле **Branch name pattern** введите `master`.
6. Отметьте следующие галочки:
   * **Require a pull request before merging** — запрещает прямой пуш в `master`, изменения можно вносить только через Pull Request.
   * **Require status checks to pass before merging** — это самое важное правило. Оно блокирует кнопку "Merge pull request", если тесты завершились с ошибкой.
      * После включения этой галочки, в поиске статус-чеков найдите задачу из вашего `ci.yml` (обычно она называется `test` или по имени Job) и выберите её.
7. Нажмите **Create** (или Save changes) внизу страницы.

Теперь система будет работать именно так, как вы описали:
- Пуш в `dev` запускает тесты.
- Слияние в `master` возможно только через Pull Request.
- Pull Request невозможно слить (скнопка Merge будет заблокирована), пока GitHub Actions не подтвердит, что тесты успешно пройдены.
