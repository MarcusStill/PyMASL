# Процесс CI/CD и правила работы с ветками

В данном репозитории настроен процесс непрерывной интеграции (CI) с использованием GitHub Actions. Он автоматизирует тестирование кода перед его слиянием в основную ветку (`master`).

## Workflow (GitHub Actions)

В файле `.github/workflows/ci.yml` настроен процесс, который автоматически запускает тесты в следующих случаях:
1. При отправке коммитов (push) в ветку `dev`.
2. При создании Pull Request (PR) из ветки `dev` в ветку `master`.

### Что делает workflow:
- Поднимает виртуальное окружение на базе Ubuntu.
- Устанавливает Python 3.12.
- Конвертирует файл `requirements.txt` в формат UTF-8 и удаляет Windows-специфичные пакеты, чтобы они не мешали запуску на Linux.
- Устанавливает все зависимости.
- Запускает тесты с использованием фиктивных доступов к базе данных и виртуального дисплея (`xvfb`), так как приложение использует графический интерфейс.

## Правильный процесс работы с ветками

У вас есть две основные ветки:
- **`dev`** — ветка для разработки и проверки новых фич.
- **`master`** — стабильная ветка, в которой всегда должен находиться рабочий код.

**Рекомендуемый флоу:**
1. Разработка ведется локально в ветке `dev` (или в ветках фич, которые сливаются в `dev`).
2. Вы отправляете изменения: `git push origin dev`.
3. GitHub Actions автоматически запускает тесты (`ci.yml`). Если тесты падают — вы чините код в `dev` и отправляете новые коммиты.
4. Если тесты в ветке `dev` прошли успешно, и код готов к релизу, вы создаете **Pull Request (PR)** из `dev` в `master` через интерфейс GitHub.
5. При создании PR тесты будут запущены еще раз. Если всё зелёное (тесты пройдены), вы или другой разработчик нажимаете кнопку **Merge PR**.
6. Код попадает в `master`.

## Как настроить защиту ветки `master` в GitHub

Чтобы никто (включая вас) случайно не сломал `master` и не мог залить в него код без прохождения тестов, нужно настроить **Branch Protection Rules**:

1. Откройте ваш репозиторий в GitHub.
2. Перейдите во вкладку **Settings** (Настройки).
3. В левом меню выберите **Branches** (в разделе "Code and automation").
4. Нажмите кнопку **Add branch protection rule** (или отредактируйте существующее правило для `master`).
5. В поле **Branch name pattern** введите `master`.
6. Поставьте галочку **Require a pull request before merging**. Это запретит прямые пуши в `master` (придется делать PR).
7. Поставьте галочку **Require status checks to pass before merging**. Это главное условие, запрещающее мержить PR, если тесты упали.
8. В появившемся поле поиска ниже (Search for status checks in the last week for this repository) найдите и выберите чек с названием вашего job-а из CI (скорее всего он будет называться `test` или по названию workflow, например `test / test`). Убедитесь, что галочка "Require branches to be up to date before merging" тоже стоит, если хотите строгого соответствия.
9. (Опционально) Включите **Do not allow bypassing the above settings**, если хотите, чтобы правила действовали даже для администраторов.
10. Нажмите **Create** (или **Save changes**) в самом низу.

Теперь код в `master` можно будет добавить только через Pull Request, и только если CI пройдет успешно!
