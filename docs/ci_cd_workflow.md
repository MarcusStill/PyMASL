# Настройка и использование CI/CD

В данном проекте уже настроен базовый пайплайн CI/CD с использованием GitHub Actions. Конфигурация находится в файле `.github/workflows/ci.yml`.

## 1. Как работает текущий CI/CD

Согласно конфигурации в `.github/workflows/ci.yml`, автоматизированные тесты запускаются в двух случаях:
* При `push` в ветку `dev` (отправка коммитов в dev).
* При создании или обновлении `pull_request` в ветку `master`.

Пайплайн автоматически:
1. Клонирует ваш код.
2. Устанавливает Python 3.12 и необходимые системные зависимости (включая xvfb для работы GUI-тестов).
3. Устанавливает зависимости из `requirements.txt` (адаптированные под Linux).
4. Запускает тесты из каталога `tests/` через pytest.

## 2. Настройка запрета на слияние при падающих тестах

Чтобы нельзя было слить `dev` в `master`, если тесты не прошли, вам нужно включить правила защиты веток (Branch protection rules) в настройках вашего репозитория на GitHub:

1. Зайдите в ваш репозиторий на GitHub.
2. Перейдите во вкладку **Settings** -> **Branches** (в левом меню).
3. Нажмите **Add branch protection rule**.
4. В поле **Branch name pattern** введите `master`.
5. Поставьте галочку **Require a pull request before merging**.
6. Поставьте галочку **Require status checks to pass before merging**.
7. В появившемся поле поиска статусов (Status checks that are required) найдите и добавьте джобу ваших тестов (обычно она называется `test` — так она названа в вашем `ci.yml`).
8. Сохраните изменения (**Create / Save changes**).

Теперь GitHub физически не позволит нажать кнопку Merge в Pull Request'е, пока тесты не пройдут успешно (появятся зеленые галочки).

## 3. Правильный Workflow (процесс работы) с двумя ветками

Ваш подход отправлять новые наработки в `dev` и сливать в `master` после проверки — это отличная практика (часто называется GitHub Flow или упрощенный GitFlow).

Вот как правильно выглядит повседневный процесс:

1. **Разработка:** Вы пишите код и делаете коммиты локально в ветке `dev`.
   ```bash
   git checkout dev
   # ... пишем код ...
   git add .
   git commit -m "Добавил новую фичу"
   ```
2. **Отправка кода:** Вы отправляете изменения в GitHub.
   ```bash
   git push origin dev
   ```
   *Сразу после этого GitHub Actions запустит тесты (т.к. был push в dev). Вы можете посмотреть результаты во вкладке Actions.*
3. **Создание Pull Request (PR):** Когда фича готова и вы хотите слить `dev` в `master`:
   * Зайдите на GitHub, перейдите в ветку `dev` и нажмите кнопку **Contribute** -> **Open pull request** (или перейдите во вкладку Pull requests -> New pull request).
   * Base branch (куда вливаем): `master`
   * Compare branch (что вливаем): `dev`
   * Создайте PR.
   * *GitHub снова запустит тесты для этого Pull Request.*
4. **Проверка и слияние:**
   * Если тесты упали (крестик), вы смотрите логи в GitHub Actions, исправляете ошибки локально, снова делаете commit и push в `dev`. PR обновится автоматически, тесты перезапустятся.
   * Если тесты прошли (зеленая галочка), вы (или другой ревьюер) нажимаете кнопку **Merge pull request**.
5. **Обновление локального master:**
   ```bash
   git checkout master
   git pull origin master
   git checkout dev
   ```

Таким образом, ветка `master` всегда остается стабильной, и в нее никогда не попадает нерабочий код, не прошедший тесты.
